# Artifact Contract

What a successful training run publishes, and what must be true before it does.

## Shape

Adapter-first. The base model is referenced by immutable revision, never copied.

```
adapter_model.safetensors   PEFT weights
adapter_config.json         PEFT configuration
tokenizer/                  tokenizer as used in training
metrics.json                training metrics
provenance.json             see PROVENANCE_SPEC.md
artifact-manifest.json      every file, its size and SHA-256
MODEL_CARD.md               human-readable summary
README.md                   generated by PEFT
```

Measured size for a rank-8 adapter on a 0.6B model: ~36 MB across 13 files. A copied base
model would be gigabytes — the size difference is itself a check, and the integration suite
asserts the published artifact stays under 200 MB.

## Rules

- **safetensors only.** No pickle-based weights anywhere in the artifact.
- **No training data.** Datasets are user-private and never ride along inside a model.
  Asserted by a test that scans every text file in the published artifact.
- **World-readable.** Permissions are normalized to 0644 before hashing, so the manifest
  describes the published bytes. safetensors writes 0600 by default, and the serving layer
  runs as a different uid than the training Job — an artifact that publishes cleanly and
  then cannot be read is worse than one that fails at package time.
- **No vocabulary or embedding mutation.** A PEFT adapter alone cannot reconstruct a model
  whose embedding matrix changed, so a tokenizer that grew past the base embedding size
  fails packaging rather than producing an artifact that cannot faithfully rebuild what was
  trained. Padding uses the existing EOS token rather than adding one.

## Publication is staged

```
train -> write to staging -> hash every file -> clean-load smoke test -> publish
```

Publication is the **last** step, an atomic rename. A consumer never observes a
half-written artifact.

The clean-load smoke test reloads the base model at its pinned revision plus the adapter
**from disk** and generates. The question it answers is "can this be served", not "does the
object still in memory work".

Each stage fails distinguishably, because the responses differ entirely:

| Stage | Code |
|---|---|
| training failed | varies by cause |
| packaged, but writing failed | `ARTIFACT_PACKAGING_FAILED` |
| packaged, but hashes or reload failed | `ARTIFACT_VERIFICATION_FAILED` |
| tokenizer or embeddings mutated | `ARTIFACT_TOKENIZER_MUTATED` |
| published | `TRAINING_SUCCEEDED` |

A failed verification leaves the staging directory unpublished. Nothing partial is exposed
under the final name.

## Serving

The adapter alone is not a model. Load the base at the exact revision recorded in
`provenance.json`, then apply the adapter. Adapter-aware serving is preferred over a merged
export; merging is not implemented and should only be added if DIMER's serving layer proves
unable to load PEFT adapters.
